# Архитектура фронтенда

Проект использует Vue 3, TypeScript, Vue Router, Pinia и Feature-Sliced Design.
Слои добавляются по необходимости: отсутствие `features` и `widgets` допустимо,
пока нет самостоятельных переиспользуемых сценариев и крупных блоков композиции.
Это соответствует [правилам слоёв FSD](https://feature-sliced.design/docs/reference/layers).

## Ответственность модулей

- `app`: запуск приложения, подключение Pinia и роутера, корневая оболочка,
  глобальные стили и связывание событий транспорта с сессией.
- `pages/<page>/ui`: представление конкретного экрана и композиция его частей.
  Логика, специфичная для одной страницы, может оставаться внутри её слайса.
  Например, `pages/pay-invoice/model/usePublicPayment.ts` управляет жизненным
  циклом публичного счёта и не зависит от роутера напрямую.
- `entities/payment`: модели счетов, справочники периодичности, API, таблица и статусы.
- `entities/channel`: каналы доставки, подключения интеграций, их API и готовность.
- `entities/session`: текущая личность, сессия и собственный профиль.
- `entities/audit`: события и подписи журнала действий.
- `shared/api`: HTTP-транспорт, ошибки, параметры запросов и серверная пагинация.
- `shared/lib`: общие форматтеры, темы и загрузчики; без справочников предметной области.
- `shared/ui`: общие элементы интерфейса.
- `shared/testing`: среда проверки Vue composables без браузерного DOM; используется тестами.

## Границы зависимостей

Слайс может импортировать другие слайсы только из нижележащих слоёв.
`app` и `shared` состоят из сегментов и допускают внутреннюю композицию.
Внешний код использует `index.ts` с явными экспортами; внутренние файлы слайса
импортируют соседей напрямую, не через собственный barrel.
Так публичный контракт не зависит от внутреннего расположения файлов.
См. [публичные API FSD](https://feature-sliced.design/docs/reference/public-api).

`npm run check:architecture` разбирает импорты скриптов TypeScript/Vue через AST,
проверяет обычные импорты, side-effect imports, реэкспорты, динамические импорты,
ссылки типов, существование файлов, публичные входы и циклы исполнения.
Стёртые TypeScript-ссылки типов не считаются циклами исполнения. Скрипт рассчитан
на текущий alias `@/` и относительные импорты; при добавлении других aliases
резолвер проверки нужно расширить вместе с тестами.

## Владение состоянием и запросами

Pinia хранит сессию. Данные экрана и формы принадлежат его компонентам/composables.
GET-загрузки получают `AbortSignal`; повторная загрузка отменяет предыдущую,
а уничтожение владельца запрещает применение позднего ответа. Проверка поколения
остаётся обязательной даже при отмене: транспорт может успеть вернуть ответ.
Очистка побочных эффектов соответствует [рекомендациям Vue](https://vuejs.org/guide/essentials/watchers.html#side-effect-cleanup).

Серверные списки используют `usePagedList`: фильтры, сортировка и общие количества
принадлежат серверу. Изменение фильтра сбрасывает страницу, сохраняет debounce
и немедленно делает старый ответ неактуальным. Удаление последней записи страницы
возвращает пользователя на последнюю существующую страницу.

Мутации требуют отдельной защиты контекста. Уже отправленный запрос может быть
выполнен сервером после ухода пользователя с экрана; его результат не должен
менять форму, статус или сообщение другого счёта. Мутации не повторяются
автоматически после неоднозначной сетевой ошибки.

## Сессия и публичные ссылки

Параллельные проверки личности объединяются. Очистка сессии делает старые ответы
неактуальными, очищает пользователя и настройки. Ошибка необязательной загрузки
настроек не отменяет успешный вход; отказ авторизации очищает сессию.

Публичные `/invoice/:token` и `/pay/:token` используют отдельные capability API
без cookies сессии. Токен кодируется как один сегмент пути. Публичный отказ
авторизации не должен разлогинивать рабочее пространство. URL с токенами
исключены из access log поставляемого Nginx; маршруты защищены `no-store`
и `no-referrer`. Журналы внешних прокси проверяются отдельно при эксплуатации.

## Обязательные проверки

Перед публикацией: `npm ci`, `npm run check`, `npm run build`.
`check` включает архитектурные тесты, проверку FSD, строгий TypeScript,
проверку неиспользуемых деклараций и Vitest. Dockerfile также запускает проверки.
Workflow `.github/workflows/frontend-checks.yml` выполняет те же команды без деплоя.
GitHub Actions закреплены полными SHA, права workflow ограничены чтением.

При развитии архитектуры переносите в `features` действительно переиспользуемое
действие, а в `widgets` — самостоятельную композицию нескольких сущностей/действий.
Не переносите единственную функцию в новый слой только ради количества каталогов.
